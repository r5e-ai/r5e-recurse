# R5E-217 bounded candidate preparation

`ManagedRequest.build/1` prepares a candidate and exact body binaries. It does not sign, submit, route, or establish that a ref was admitted. Trusted integration must resolve SessionBinding, LlmCall and ContextManifest; obtain `first_request` from serialized session state; and forward the exact routing values and bytes only after both required admissions. No gateway integration is implemented here.

The JSON pointer selects one decoded string. Ordered-object parsing rejects duplicate keys anywhere, including equivalent escaped keys. Original body bytes are retained and hashed without re-encoding; JSON numeric values are never used to construct replacement bytes. JSON outside Jason's numeric decoding range refuses as invalid JSON.

## Unresolved canonical provenance gap

T047 asks later requests to record harness-added input with provenance. The current ManagedRequest Kind has no provenance property and rejects additional properties. Its `firstInput` field remains required even for later requests. This implementation continues identifying/hashing that input on later requests while skipping manifest equality, and separately returns harness-input descriptors with a verified string digest and a syntactically validated provenance event ref. Those descriptors are **not recorded in the candidate**. Consequently the canonical provenance portion of T047 is not complete.

A proposed schema amendment is an optional `harnessInputs` array containing objects with required `fieldPath` (RFC 6901 string), `digest` (SHA-256 of decoded UTF-8 string), and `provenance` (admitted event ref), rejecting additional properties. The integration contract would need to specify which provenance event Kinds qualify and how complete adapter coverage is established. This proposal needs a recorded spec decision and review before changing the unreleased Kind. No schema amendment is included here.
