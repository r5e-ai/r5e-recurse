# R5E-212 recovery admission boundary

`Boot.Admission.new/4` requires trusted `journal:` and `generation:` options. The journal owns a persistent namespace; the generation is the current recovery service's boot/run pair. There is no direct, unjournaled submission fallback. Original Badge issuer custody remains with the supplied signing callback; startup does not issue replacement authority.

Revocation identity is origin plus Badge event and recovery stage. Observation identity is origin plus interruption, optional SessionBinding/action references and stage. Neither identity includes the current boot ID. Reusing an identity with a changed spec conflicts. A prepared operation also binds the exact recorded issuer and authority, including when another caller completes it between the metadata lookup and submission. A reserved operation has no confirmed signature or authority and remains uncertain; it cannot be replaced.

Recovery checks the journal before preparing a new-generation submission. Existing operations only look up canonical history. Lost acknowledgment, a reserved intent, missing history, recorded denial or service failure never cause another signature or POST. A new recovery operation still verifies the actual Badge issuer before journaling its issuer-authorized revocation. Successful recovery confirms the exact envelope, target, spec, origin and actor in canonical history.

The journal helper reads at most 64 KiB plus one byte of a response body. A syntactically valid receipt reference is only an untrusted `event_ref_hint`; it cannot establish admission. An acknowledged response with a malformed or oversized receipt still triggers canonical lookup without that hint. If history cannot confirm the outcome, recovery retains uncertainty and any hint. A recovered canonical grant supplies the confirmed event reference.

The read-only `NonceJournal.operation/2` API returns only immutable origin, generation, candidate, status and prepared request metadata. It does not reveal keys, permit replacement, sign or submit.

Validation covers actual disposable HTTP-kernel revocation and observation recovery across boots; lost acknowledgments; reserved attempts with no subsequent signature or POST; changed candidates; unavailable journals; and competing same-spec results with different authority. Existing observation fixtures deliberately use a minimal interruption Kind to isolate this boundary: these are not full managed boot tests.

Remaining R5E-212 work includes consistent canonical interrupted/partial-setup discovery, actual process-ownership reconciliation, correctly admitted interruption lifecycle records, deployment supervision and command/route gate wiring. Preparation must already be durable before credentials/span/binding; recovery must not fabricate a preparation event for malformed old history. Missing authority or unresolved recovery keeps the gate closed. Recorded bindings never recreate keys, routes or execution workers.
