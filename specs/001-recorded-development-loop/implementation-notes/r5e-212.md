# R5E-212 recovery admission boundary

`Boot.Admission.new/4` requires trusted `journal:` and `generation:` options. The journal owns a persistent namespace; the generation is the current recovery service's boot/run pair. There is no direct, unjournaled submission fallback. Original Badge issuer custody remains with the supplied signing callback; startup does not issue replacement authority.

Revocation identity is origin plus Badge event and recovery stage. Observation identity is origin plus interruption, optional SessionBinding/action references and stage. Neither identity includes the current boot ID. Reusing an identity with a changed spec conflicts. A prepared operation also binds the exact recorded issuer and authority, including when another caller completes it between the metadata lookup and submission. A reserved operation has no confirmed signature or authority and remains uncertain; it cannot be replaced.

Recovery checks the journal before preparing a new-generation submission. Existing operations only look up canonical history. Lost acknowledgment, a reserved intent, missing history, recorded denial or service failure never cause another signature or POST. A new recovery operation still verifies the actual Badge issuer before journaling its issuer-authorized revocation. Successful recovery confirms the exact envelope, target, spec, origin and actor in canonical history.

The journal helper reads at most 64 KiB plus one byte of a response body. A syntactically valid receipt reference is only an untrusted `event_ref_hint`; it cannot establish admission. An acknowledged response with a malformed or oversized receipt still triggers canonical lookup without that hint. If history cannot confirm the outcome, recovery retains uncertainty and any hint. A recovered canonical grant supplies the confirmed event reference.

The read-only `NonceJournal.operation/2` API returns only immutable origin, generation, candidate, status and prepared request metadata. It does not reveal keys, permit replacement, sign or submit.

Validation covers actual disposable HTTP-kernel revocation and observation recovery across boots; lost acknowledgments; reserved attempts with no subsequent signature or POST; changed candidates; unavailable journals; and competing same-spec results with different authority. Existing observation fixtures deliberately use a minimal interruption Kind to isolate this boundary: these are not full managed boot tests.

Remaining R5E-212 work includes consistent canonical interrupted/partial-setup discovery, actual process-ownership reconciliation, correctly admitted interruption lifecycle records, deployment supervision and command/route gate wiring. Preparation must already be durable before credentials/span/binding; recovery must not fabricate a preparation event for malformed old history. Missing authority or unresolved recovery keeps the gate closed. Recorded bindings never recreate keys, routes or execution workers.

## Read-only canonical discovery

`Boot.Discovery.read(client, origin, current_boot_id)` loads immutable event/CAS
history through `Commands.KernelStore.history/1`, then requires a second full
`KernelClient.events_from/2` result to match exactly. A changing head is an error,
with no retry. The returned checkpoint is a snapshot boundary; it does not lock
out later admissions. This online boundary trusts the configured kernel to serve
its authentic, complete latest history and to have enforced Kind policy. Local
chain/CAS hashes, every relevant request signature and copied identity/target
fields are verified with `RecurseVerify.Identity` and `Commands.Envelope`; they
are not independent proof of an authentic offline head or policy admission.

Discovery normalizes admitted workflow records and strictly replays `Lifecycle`.
Replay errors remain errors. It enumerates all qualified immutable
`SessionBinding` events, including a binding admitted before a lifecycle event
could cite it. Each entry retains exact Task, binding, credential, span,
preparation and prior lifecycle references, generation, Badge issuer and subject.
It checks the actual Task, Task-scoped Badge and Endorsement, delegated issuer,
session signer, span actor and exact named span reference. Missing preparation
before any cited credential/span/binding, inconsistent provenance/generation or
multiple bindings for one Task produce explicit blockers. A binding admitted after
terminal or interruption closure retains its status classification with a
`binding_after_closure` blocker. Independently inventoried retry bindings share
Lifecycle's session freshness predicate and report `retry_reused_session` before
any lifecycle citation. Entries include the exact `delegation` event reference. No preparation fact
or lifecycle transition is synthesized.

`current_boot`, `old_terminal`, `old_interrupted` and `old_active` classify
resolved bindings. `unattached` additionally lists bindings that no replayed
attempt currently cites, so it can overlap the other lists. Provenance failures
remain visible in `bindings` with blockers instead of becoming recovery grants.
Only credentials explicitly cited by bindings enter this bounded implementation;
unrelated Badges never become revocation targets. Canonical partial setup before
a binding is an explicit `partial_setup_provenance` integration dependency, not
an empty-list assertion that no partial setup exists. Journal-only reserved
intents, process ownership and admission-gate wiring are also explicit
integration dependencies. `complete_boot` is always false.

Discovery does not sign, submit, revoke, inspect or kill processes, infer stopping
from PID absence, restore keys/routes, or open the boot gate. Its focused tests
use signed HTTP protocol fixtures (not kernel-policy admission evidence) for
classification, uncited and duplicate bindings, missing preparation, provenance
mismatch, invalid replay, copied identity/signature/origin failures and a changing
head. The deployment's real-Kind disposable-kernel admission tests remain a
separate integration obligation.

Validation after adversarial corrections: ordinary suite 139 tests, zero failures, 47 skipped, 3 excluded; format and warnings-as-errors compilation passed. A separate actual kernel run passed 15 tests (12 policy fixtures plus three Discovery cases). The actual kernel admitted server-named AgentSession records and bindings after failure/interruption; discovery retained those later bindings with explicit closure blockers. Retry-key reuse is covered by signed protocol fixtures, not an actual kernel retry acceptance demonstration. No complete boot or managed process launch is established.
