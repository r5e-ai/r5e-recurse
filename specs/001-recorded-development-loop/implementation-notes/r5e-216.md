# R5E-216: immutable admission attempts

The journal reserves an operation with a durable intent before invoking the signer. It then stores the exact candidate, canonical request and verified envelope before HTTP submission. An operation's candidate and generation cannot change. Subsequent calls only read canonical history; neither an absent result nor a transport failure permits another signature or submission.

A single Python helper holds the OS writer lock, publishes both files, and initiates HTTP dispatch. Dispatch is not gated by a separate process-liveness check. Publication fsyncs the file and directory; startup also fsyncs the journal directory's parent. If publication succeeds but its acknowledgment is lost, the intent still prevents re-signing. If the helper dies during signing, the prepared entry cannot be published through another writer. Death before the helper sends POST prevents dispatch; an already-sent HTTP request may still complete and is resolved only by lookup. This is a cooperative local profile, not protection from malicious same-user filesystem access.

A crash between intent and prepared entry leaves the operation reserved and uncertain. Recovery never guesses whether signing happened. Such an operation remains lookup-only; this favors refusing progress over silently creating a replacement attempt. A separately authorized reconciliation path must decide further work.

Candidate specs must recursively use JSON string keys; atom keys and encoding collisions are refused before reservation. The complete prepared entry must also survive an exact canonical JSON round trip, including the signer-returned envelope. Integer JSON tokens are limited to 1,024 bytes including any minus sign, matching the pinned Jason decoder; the helper explicitly accepts that numeric domain. This is a local transport limit, not a new core protocol rule. Initial recorded HTTP responses are resolved through canonical history, so a replay denial returns the original consuming result just as later recovery does.

Restart validates each filename, candidate digest, signature and signed request binding, requires each prepared entry's matching intent, and rejects duplicate actor/nonce pairs. Malformed history or unsupported denial stages stop recovery. Actor-mismatch and replay denials do not consume the nonce; other recognized recorded denials do, including expired-request denials. The first consuming receipt must match the exact persisted request and candidate.

`SessionBinding.KernelDriver.recover/2` takes operation handles and needs no live session key or currently valid credential. It returns recovered admission evidence, never enables routes. The configured online kernel is trusted; chain and CAS integrity checks are not independent checkpoint pinning.

Validation includes actual disposable HTTP kernels for lost acknowledgments, recorded denials and no-match uncertainty; independent deterministic crashes during signing and after immutable publication; failed-helper fencing; scanner attribution; malformed restart entries; and actual fixed-wrapper kernel admission of distinct session bindings followed by recovery after key destruction. Managed gateway dispatch, boot discovery, and the spec-bytes signer remain separate work.

Public defect: https://gitlab.com/r5e-group/r5e-recurse/-/work_items/4.

The journal has not been deployed; exercised namespaces are disposable test data. An incompatible pre-release namespace refuses startup without deleting its reservations. No automatic migration or production compatibility claim is made.

Recovery validates expiry syntax with core `Instant`, including lowercase RFC3339 separators, unknown zero offset and nanosecond fractions. It deliberately does not require expiry to be in the future: an expired request may already have a canonical consuming denial. Timestamp compatibility regression coverage was added with signer defect #6.
